Act 2 · Read your own code

Your two files, plate by plate

The header file (stack2.h) is the blueprint of the machine: it declares the rack and the buttons, but does nothing yet. The second file (your stack1_main.c, really C++) is where each button gets its recipe. Tap any line below to see what it means in kitchen language.

stack2.h · the machine blueprint
//#include <iomanip>          // (commented out, unused)
//using namespace std;       // (off means you need std:: in front)

struct _stack {              // the RAW PLATE RACK: 3 shelves, no rules
    int *s;                  // the shelf itself: where plates actually sit
    int size;                // how many plates fit (capacity)
    int tos;                 // the finger: index of the top plate (-1 = empty)
};

class stack1 {               // the DISPENSER MACHINE that wraps the rack
    _stack sta;              // its private rack, locked inside (private by default)
public:
    stack1();                // constructor: power-on self-check, runs on its own
    stack1(int);             // constructor, but you pick the capacity
    bool isfull();           // "any room left?"   -> answers yes/no
    bool isempty();          // "any plates left?" -> answers yes/no
    void push(int);          // PUT a plate on top
    int  pop();              // TAKE the top plate off (returns it)
    void display();          // read out every plate, bottom to top
    ~stack1();               // destructor: shutdown + cleanup, runs on its own
};

Thing to notice: class stack1 has a public: door. Everything after it (the buttons) can be used from outside. The _stack sta line sits before that door, so it is private: locked inside the machine, nobody can reach in and mess with the plates directly.

Act 3 · C vs C++: two ways to run a kitchen

Same dish, two kitchens

The stack algorithm is identical in both languages. The difference is who keeps order. In C, you are the only manager and you must remember everything. In C++, the machine (class) manages its own life.

Kitchen #1

The C kitchen

one chef, recipes on the wall, everything manual
  • Ingredients and recipes are separate. A struct is just a box of ingredients. The functions (push, pop) are papers hanging on the wall, and every time you need one you hand the whole box over: push(&sta, 5).
  • You must set up the station yourself. There is no automatic prep. You write an init_stack(), and if you forget to call it before cooking, you are working with garbage on the counter.
  • You must clean up yourself. At the end you call free_stack() / free(). Forget it, and the rented shelf is never returned: that is a memory leak, leftover grease that ruins the next dish.
  • No locked doors. Every part of the struct is public. Any function anywhere can reach in and mess up tos. Order exists only because you are careful.
vs
Kitchen #2

The C++ kitchen

the plate dispenser machine that takes care of itself
  • The machine is the recipe + the ingredients. A class bundles the data (private rack) AND the buttons (public methods) into one sealed unit. You cook by pressing buttons: sta.push(5); the rack is inside, you never touch it.
  • Prep is automatic. The constructor runs the moment you create a dispenser: it sets tos = -1 and rents the shelf (new int[size]). You cannot forget the setup, because it happens on its own.
  • Cleanup is automatic. The destructor runs when the object dies and returns the shelf (delete[] sta.s). No manual call, so the leak-prone step is hard to forget.
  • Locked doors. private: hides the rack from everyone. Outsiders can only press push, pop, display. They physically cannot corrupt tos or grab a middle plate.

Same plates, same pile, same LIFO. Only the organization changes: C trusts you to be careful, C++ locks the doors and sweeps the floor for you.

Prove you got it

Five self-checks

  1. I push 10, 20, 30, then pop once. What number comes out, and what is left on the pile?
  2. After pushing 3 plates onto an empty stack, what number is tos?
  3. Why can pop() sometimes hand you back -999?
  4. What exactly prints when you push onto a full stack?
  5. In the C version with no destructor, what do you have to remember to do at the end, and what happens if you forget?
Peek at the answers

1. 30 comes out (the top). Plates left: 10, 20. 2. tos = 2 (the finger counts 0, 1, 2). 3. The pile was empty, so it returns the decoy sentinel -999 instead of a real plate. 4. “stack is full” (the else branch of push). 5. Call free_stack() / free(sta.s). Forget it, and the memory is never returned: a memory leak.
